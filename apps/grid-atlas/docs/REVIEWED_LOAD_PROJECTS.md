# 검토한 개별 수용가 신청·계약

수용가 개별 분모를 NYISO 큐에만 제한하지 않는다. 주 공익사업위원회(PUC), 전력회사, 허가 기관의 공식 문서에서도 **식별 가능한 단일 부지의 전력 서비스 신청 또는 계약**을 확인하면 개별 원장에 포함할 수 있다. 전국 공통 큐 번호나 해당 회사의 완전한 원장 공개는 필수 조건이 아니다.

`data/reviewed-load-projects.json`은 기존 `Project`·`Source` 구조와 별도의 검토 기록을 연결한다. 검토에는 기관·사건 번호, 단일 신청을 식별한 근거, 용량의 의미, 실제 취득시각·SHA-256·인용문, 원자료 기준일, 단계 판단 이유와 남은 공백이 있다. `shared/reviewed-load-projects.ts`가 이를 검증하며 새 DB 필드나 임의의 큐 번호를 만들지 않는다.

PG&E는 2025년 6월 산업용으로 확인한 196개 서비스 요청 ID를 **2025-12-31 기준 후속 원장**에서 추적했다. 195개가 일치하고 1개는 후속 원장에 없어 상태 미확인이다. 이 코호트는 진행 중 111개·통전 53개·취소 31개·미확인 1개이며 최신 원장의 산업용 전체 모집단이 아니다. 진행 중 28개는 기준일 이전의 공식 Step 7 공사 시작일을 확인해 공사 단계 모형을 적용하고, 나머지 불명확한 단계는 미산출로 둔다. 고객명·부지·요청 MW가 공개되지 않아 모두 데이터센터나 대형 공장이라고 주장하지 않으며, 원자료의 2025년 말 상태를 2026년 10월 현재 상태로 바꾸지 않는다.

## 포함·배제 기준

- 본토 48주/DC의 식별된 개별 전력 서비스 신청·계약이고 원자료 기준일에 활성 상태여야 적격이다. 그 이후 상태를 새로 확인하지 못했으면 과거 기준일을 그대로 표시한다.
- 복수 부지가 합쳐진 사건, 기관·회사 총량, 부지 인허가만 확인한 사업, 단일 신청인지 불분명한 기록은 개별 활성 분모에서 제외한다. 운영·철회 기록은 보존하되 활성 평균에서 제외한다.
- 공급계약 MW 또는 계통 요청 MW만 `loadMw`에 넣는다. IT 설비 용량·발전 설비 용량·회사의 전체 파이프라인을 해당 고객의 요청량으로 바꾸지 않는다. 공개하지 않은 MW는 null이다.
- `active` 또는 `In-progress`만으로 다섯 요건의 진행률을 결정하지 않는다. 이 경우 활성 건수에는 포함되지만 점수는 null이고 평균 분모에서 제외한다.
- 단계 추정이 가능한 사례는 `stage-proxy-v1`의 검토된 단계 ID와 별도의 판단 이유를 명시한다. 공급계약을 계약 체결 단계에 대응시키더라도 실제 기술검토·인허가의 완료가 입증되는 것은 아니다. 직접 요건 평가와 같은 사실로 저장하지 않는다.
- 사건·원장별 식별자 기준이며 서로 다른 회사 자료의 동일한 물리 사업을 모두 연결한 것은 아니다. 중복이 의심되는 집계·다부지 계약을 임의로 개별 사업 수에 더하지 않는다.

API는 `coverage: case` 출처의 활성 적격 프로젝트를 받을 때 체크인된 검토 자료와 **Project 전체 필드가 정확히 일치하는지** 확인한다. 용량·상태·출처일·ID가 바뀌면 다시 검토해야 한다. 기존 전체·선별 원장 검증과, 본토·활성·단일 레코드 조건은 유지한다. `status=eligible` 목록과 CSV는 점수가 없는 활성 신청도 포함하며 `scored`·`unknown` 필터와 구분한다.

## 재생성과 검증

앱 디렉터리에서 실행한다.

```sh
# 검토 자료를 초기 JSON에 반영. 실제 로컬·운영 DB에는 연결하지 않는다.
npm run data:reviewed

# 파일을 쓰지 않고 정확한 반영 상태·파생 집계·실제 JSON 해시를 검증한다.
npm run data:reviewed:check
```

기존 ID는 그대로 갱신하고 새로운 공식 사건만 추가한다. 동일 출처·원문 ID가 이미 다른 프로젝트 ID에 연결되었거나 기존 ID를 다른 사건에 재할당하면 중단한다. 관련 없는 프로젝트·평가·기존 수집 해시는 보존한다. 새 검토 JSON의 해시는 `provenance.reviewedLoadImports`에 별도로 남으며, 과거 보관본의 `referenceSha256`이나 원문 취득시각을 새로 꾸미지 않는다.

기본 명령은 `source-registry.json`도 병합된 출처 목록과 동기화하고 `--check`에서 일치를 확인한다. 사용자 지정 입력·출력 경로로 검증할 때는 저장소의 출처 목록을 수정하지 않는다. 추가 사례 출처의 `adapter: null`은 유지하므로 출처를 등록했다고 자동 파서·정기 갱신이 가동되는 것은 아니다.

보관본에서 `build-bootstrap.py`를 다시 실행할 때도 검토 자료를 적용한다. 로컬·원격 최초 초기화와 GitHub Pages의 임시 DB 생성은 같은 검증기를 거쳐 메모리에서 검토 자료를 합친다. 새 빌드에 반영되지만 이미 초기화된 DB 원장·평가 이력을 덮어쓰지는 않는다. 실제 운영 DB 갱신은 기존 인증된 적재·관측 절차가 별도로 필요하다.

반복 빌드는 새로운 원문 취득이나 프로젝트 상태 갱신이 아니다. 자료가 없는 권역·회사·날짜는 여전히 공백이며, 선별 사례가 추가되었다고 전국 전수를 확보한 것으로 표시하지 않는다.
