# Grid Atlas 데이터 운영

이 앱은 발전·저장·수용가의 계통 접속 근거를 같은 다섯 요건으로 관측하는 별도 프로젝트입니다. 이전 대시보드의 화면·자료는 참고에 사용했으며, 기존 Site와 데이터베이스로 게시하거나 쓰지 않습니다.

## 점수와 분모

다섯 요건은 기술검토, 계약·비용·보증, 부지·인허가·권원, 설비·계통 보강, 운영 준비·통전 승인입니다. 각각 기본 20점을 배정합니다. 확인된 미진행은 20점, 완료는 0점이며, 확인된 진행률 `p`가 있으면 `20 × (1 − p)`입니다. 다섯 요건 모두 미진행으로 확인된 프로젝트는 100점입니다.

요건들은 반드시 순서대로 진행하는 단계가 아닙니다. 알려진 일부 단계만으로 다른 요건의 진행을 추정하지 않습니다. 미공개·미확인은 값이 없으므로 별도 집계합니다. 모든 해당 요건을 평가한 프로젝트만 산술평균에 포함하고, 평가된 프로젝트 수·미평가 수·용량 미공개 수를 함께 표시합니다. 적용 제외 요건은 근거를 기록하고 나머지 요건의 가중치를 다시 100점으로 맞춥니다.

뉴스 등 정성 자료의 추정은 공식 확인과 구분합니다. 출처, 적용일, 실제 기록시각, 판단 이유를 저장하고 제한된 진행률 값으로 평가합니다. 수집기가 뉴스의 표현을 읽고 자동으로 0점이나 100점을 확정하지 않습니다. 접속 점수는 완공 확률·지연 개월 수·기자재 수주 확률이 아닙니다.

기본 대상은 미국 본토 48주와 DC의 확인 가능한 활성 개별 신청 레코드입니다. 출처별 신청 ID를 보존하고, 발전과 저장의 복합 신청은 같은 ID일 때 전체에서 한 번 집계합니다. 출처 사이 물리 프로젝트의 동일성은 별도 검증이 필요합니다. 따라서 현재 결과는 **수집·식별·평가된 신청 레코드의 점수**이며, 전국 모든 물리 프로젝트의 전수 평균으로 부를 수 없습니다.

발전 MW, 저장 MW, 부하 접속요청 MW를 분리합니다. MVA, 실부하, IT 부하, 계약용량은 임의로 변환하거나 더하지 않습니다. 미공개 용량은 `null`로 유지합니다. 권역 집계 공시, 개별 프로젝트, 사례 기사, 송전 지원사업의 범위를 혼합하지 않습니다.

## 수집 실행과 상태

실행 위치는 `apps/grid-atlas`입니다. 로컬 원자료 확인만 할 때는 다음 명령을 사용합니다.

```sh
python3 scripts/collect.py --source-id nyiso-load-register --source-id lbnl-generation-storage-queues --cadence weekly --state-dir .local/collection
```

새 원격 사이트에 반영할 때는 환경의 `GRID_ATLAS_URL`과 `GRID_ATLAS_ADMIN_TOKEN`을 사용합니다. 비밀값을 명령행 인수로 넣지 않습니다.

```sh
python3 scripts/collect.py --cadence weekly --api-url "$GRID_ATLAS_URL" --state-dir .local/collection
```

| 상태 | 의미와 다음 조치 |
| --- | --- |
| `normalized` | 원자료에서 프로젝트 레코드 추출·검증 완료. 원격 적재 여부는 별도 확인 |
| `imported` | 해당 출처의 검증된 레코드를 API에 반영 |
| `parser_review` | 원자료 확보, 아직 자동 정규화되지 않음. 필드·범례·기준일을 검토하고 파서 구현 필요 |
| `skipped_private` | 공개 수집 대상이 아님. 정당한 접근 경로와 자료 제공 협의 필요 |
| `failed` | 다운로드·검증·API 작업 실패. 보고서의 해당 출처 오류 확인 |

실행 보고서의 전체 상태는 `success`, `partial`, `failed`입니다. 모든 요청 출처가 정규화·적재된 경우에만 종료 코드 0이며, 일부 검토 대기 또는 실패는 코드 1입니다. `success`도 그 실행에서 요청한 출처의 성공만 의미하며 전국 수집 완료가 아닙니다.

원자료 다운로드 → 검증·정규화 → 출처 단위 API 적재 → 관측 저장 → 실행 기록의 순서입니다. 한 출처의 전체 신청 목록 교체는 원자적으로 처리합니다. 여러 출처의 실행 전체는 단일 트랜잭션이 아니므로, 일부만 성공하면 성공한 반영분과 실패분을 함께 보고합니다. 실패한 출처의 기존 정상 자료를 빈 목록이나 0으로 덮어쓰지 않습니다.

현재 자동 파서는 NYISO 수용가 원장과 LBNL 발전·저장 활성 신청 원장을 지원합니다. LBNL 공식 목록과 연결된 원장 파일을 각각 보관하고, 파일의 필드·활성 범위·기준일을 검증한 뒤 적재합니다. 목록 페이지 다운로드만으로는 갱신에 성공한 것으로 처리하지 않습니다. 현재 검증한 LBNL 기준일은 2025년 12월 31일이며, 실제 수집시각과 구분합니다. 주간·월간 실행은 새 공개 자료를 확인하는 주기이지 원자료 자체의 주간·월간 발행을 뜻하지 않습니다.

기본 두 출처가 모두 검증되면 전체 실행은 `success`일 수 있습니다. 이는 해당 두 출처의 성공이며 나머지 수용가 자료까지 최신화하거나 전국 공백을 해소한 것이 아닙니다. 기타 권역은 출처 목록과 검토 상태를 유지하고, 개별 공식 원장과 파서를 확보해야 합니다. 비공개 수용가 신청 자료와 전국 분모의 공백은 자동 수집만으로 해소할 수 없습니다. 데이터 범위와 초기 적재 내용은 [DATA.md](DATA.md)를 확인합니다.

## 원자료와 시간 이력

각 실행은 다음 로컬 파일을 남깁니다.

- `.local/collection/runs/<실행 ID>/report.json`: 실행시각, 출처별 결과, 오류, 관측·API 기록 여부
- 같은 실행 디렉터리의 `*-source-rows.json`, `*-import.json`: 추출한 원자료 행과 검증된 적재 요청
- `.local/collection/raw/<SHA-256>.bin`: 해시로 식별하는 원자료
- `.local/collection/state.json`: 마지막 정상 정규화 결과의 상태

원자료 기준일, 공시일, 수집시각, 평가의 실제 적용일, 기록시각을 구분합니다. 단순히 오늘 다시 다운로드했다고 원자료의 기준일을 오늘로 바꾸지 않습니다. 날짜를 확인하지 못하면 없는 값으로 유지합니다.

관측과 평가 이력은 추가 저장합니다. 특정 기준일의 조회와 당시 시스템이 알고 있었던 범위의 조회를 구분합니다. 늦게 확인한 과거 사건을 기록할 수 있지만 그 기록을 과거부터 알고 있었던 것처럼 보이지 않게 합니다. 최초 관측 이전의 재현 가능한 자료가 없으면 **자료 없음**입니다. 오늘의 상태를 과거 날짜에 복사해 시계열을 만들지 않습니다.

GitHub Actions는 수집 보고서와 원자료를 실패한 실행에서도 Artifact로 보관하고, 마지막 상태 파일만 캐시로 재사용합니다. 캐시가 없어도 다시 수집할 수 있어야 하며 캐시는 증거의 영구 보관소가 아닙니다. Artifact 보존 기간은 기본 90일입니다. 장기 재현성을 위해 기간 만료 전에 원자료를 별도 보관해야 합니다. 이 버전에 영구 원자료 저장소의 자동 아카이빙은 포함되지 않습니다.

## 정기 운영 확인

1. GitHub Actions에서 예약 작업의 최근 실행 여부와 결과를 확인합니다. 녹색 구성 확인 작업만 있고 수집 작업이 생략된 경우 갱신된 것이 아닙니다.
2. 수집 실행 보고서에서 `partial`·`failed` 및 `parser_review` 출처를 확인합니다.
3. 대시보드의 원자료 기준일과 수집시각, 알려진 개별 신청 수, 용량 공백을 확인합니다. 수집 성공은 평가 완료를 의미하지 않습니다.
4. 실제 근거가 있는 요건만 평가합니다. 변경된 근거는 새 평가로 기록하고 이유를 남깁니다.
5. 관측과 평가 이력이 생성됐는지, 미공개가 100점으로 바뀌지 않았는지 확인합니다.
6. GitHub Artifact와 D1 백업·보존 정책을 확인합니다. D1 복구 기능의 범위와 보존 기간은 사용하는 Cloudflare 요금제·설정에 따릅니다.
7. Worker의 CPU 사용량·예외·응답 실패를 확인합니다. 현재 전체 초기 적재와 요약은 로컬에서 수백 밀리초 규모의 CPU 처리를 사용하므로 무료 Workers 한도에서는 실패할 수 있습니다. 로컬 성공만으로 무료 계정 운영이 검증됐다고 판단하지 않습니다. 실제 요금제의 CPU·D1 한도 안에서 초기 적재, 요약, 스냅샷 저장을 검증하고 필요하면 집계 분리 또는 요금제·CPU 한도 조정을 진행합니다.

주간·월간 작업은 같은 쓰기 작업 그룹으로 묶어 중복 실행을 직렬화합니다. 활성화·주기 변수를 변경하면 재배포해 사이트의 일정 설정 표시에도 반영합니다. 이 표시는 배포 시 선언이며 실행 보장이 아니므로 최근 실행 기록을 따로 확인합니다. GitHub 실행 지연·누락은 데이터 조회 화면 자체의 장애와 구분해 다룹니다. 현재 워크플로에는 별도 메일·메신저 알림이나 실행 보장 서비스가 없습니다.

## 실패 대응과 비밀값 교체

- `ENABLE_GRID_ATLAS_REFRESH`가 없거나 `false`: 비활성 상태입니다. 게시·데이터 확인 후에만 활성화합니다.
- URL·토큰 누락: 수집 전에 실패합니다. GitHub 설정을 수정한 후 수동 재실행합니다.
- HTTP 401/403: 쓰기 토큰 일치와 배포 대상을 확인합니다. 토큰 값을 로그에 출력하지 않습니다.
- 파서 검증 실패: 기존 데이터를 보존하고 새 원자료·열 이름·범례를 확인합니다. 자동으로 누락 행을 삭제하거나 값의 의미를 추정하지 않습니다.
- Bootstrap HTTP 409: 이미 데이터가 있는 DB입니다. 반복 초기화 대신 출처 단위 갱신을 사용합니다.
- 마이그레이션 실패: 배포를 중단하고 새 D1 대상·적용 이력을 확인합니다. API 요청으로 스키마를 만들거나 기존 DB를 삭제하지 않습니다.

관리 토큰 교체 시 GitHub Secret `GRID_ATLAS_ADMIN_TOKEN`을 새 값으로 바꾼 뒤 수동 배포를 실행해 Worker `ADMIN_TOKEN`도 갱신합니다. 둘이 일치하지 않는 동안 쓰기 요청은 실패해야 합니다. 조사 중에는 `ENABLE_GRID_ATLAS_REFRESH=false`로 예약 반영을 멈출 수 있습니다. 조회 자료를 공개하기로 한 범위를 확대하는 작업은 별도로 검토합니다.

코드 검사는 `npm run typecheck`, `npm test`, `npm run test:python`, `npm run build`입니다. 로컬 검사 통과는 Cloudflare 배포·인증·예약 실행 성공의 증거가 아닙니다. 실제 계정 연결 후 첫 게시와 수집 결과를 각각 확인합니다.
