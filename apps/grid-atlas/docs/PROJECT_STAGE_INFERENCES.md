# 개별 프로젝트 진행상황의 정성 판단

`project-stage-inferences.json`은 공식 원장, 규제기관 문서, 고객 공시와 보도에서 개별 사업의 진행상황을 판단한 자료다. 검토자가 선택한 단계와 병목, 판단 이유, 가정, 신뢰도, 출처를 함께 보존한다. 이 자료의 `qualitative-stage-v1` 점수는 다섯 요건의 실제 완료율이나 지연 확률이 아니다.

원문 단계에 고정 대응하는 기존 `stage-proxy-v1`, 개별 정성 판단, DB에 저장된 요건별 평가를 구분한다. 정성 판단을 추가해도 직접 요건 평가가 생성되지는 않는다. 저장된 요건별 근거가 하나라도 선택되면 단계 추정으로 부족한 요건을 채우지 않는다.

## 판단과 평균 포함은 별개다

2026-10-13부터 대표 평균은 용량 가중이다. 이 문서의 `applyToAverage`는 판단의 활성 평가 적격성으로 유지하며, 실제 용량 평균에는 선택한 유형의 양수 공개 MW가 추가로 필요하다. 점수만 있는 판단을 MW 분모에 넣지 않는다. [용량 집계 기준](CAPACITY_WEIGHTING.md)을 참조한다.

개별 날짜·신청 번호·부지 이름을 대조해 진척을 판단한다. 이름이 비슷하거나 같은 회사라는 이유로 다른 시설의 계약·공사를 연결하지 않는다. PG&E 설계 착수일, Georgia Power의 실행된 고객 약정, 특정 고객을 위한 송전 보강안처럼 실제로 확인된 차이를 반영한다. 접수일, 목표일의 경과 또는 뉴스 부재만으로 미진행 100점이나 운영 완료 0점을 부여하지 않는다.

단계를 판단할 수 있어도 현재 활성 여부, 단일 사업의 식별, 중복 관계 또는 판단 기준일이 불명확하면 점수는 참고용으로 표시하고 평균에서는 제외한다. `applyToAverage`가 참이려면 날짜가 있는 판단, 활성 상태, 본토의 적격 신청 원장과 일치하는 `projectSnapshot`, 검토한 사업 식별이 필요하다. 식별이 명확한 `clear` 또는 중복 집단에서 한 번 집계하도록 검토한 `representative`를 허용하며, 단순 `possible_duplicate`·`unresolved`는 제외한다. 평균 포함 판단은 원장 자체를 자동으로 승격하지 않는다.

운영·철회·현재 상태 미확인 사업에도 근거가 있는 과거 단계의 참고 점수를 표시할 수 있다. 이런 점수와 실제로 평균에 들어간 점수의 수는 다르다. 공개되지 않은 고객이나 용량은 별도 공백으로 남긴다. 같은 부지의 중복 신청·확장 하위 사업·송전 참고 기록을 각각 독립 사업처럼 합산하지 않는다.

`confidence`의 high·medium·low는 근거와 해석의 확실성에 대한 검토자 판단이다. 통계적 확률이나 가중치가 아니며 신뢰도가 낮다는 이유로 임의의 점수를 가산하지 않는다. 현재 상태도 원문에 명시됐는지(`explicit`), 문서의 진행상황에서 추론했는지(`inferred`)를 구분한다.

감사 결과도 `judged`(판단 작성), `no_judgement`(검토했지만 판단 보류), `not_reviewed`(개별 근거 검토 전)로 나눈다. 조사 원장에 존재하거나 기본 감사 행을 만들었다는 이유로 검토 완료 수에 넣지 않는다. 검토 대기는 근거 부족으로 판정된 사업과 다르다.

## 공통 모형과 실제 확인 사실

선택한 단계에는 기술·상업·인허가·공사·통전 순서로 다섯 진행률을 가정한다. 점수는 각 요건의 `20 × (1 − 진행률)`을 더한 값이다. 진행률은 공통 모형의 위치이며 개별 문서에서 그 비율을 측정했다는 뜻이 아니다. 기존 공식 단계별 모형은 [배점과 평가 범위](SCORE_COVERAGE.md)를 참조한다.

| 정성 해석에 사용하는 단계 | 모형 점수 | 해석의 범위 |
| --- | ---: | --- |
| `technical_scoping` | 90 | 개별 요청의 기술 범위·초기 협의 |
| `connection_design` | 75 | 접속 설계·연결 방안 검토 |
| `grid_upgrade_planning` | 65 | 확인된 망보강 방안과 실행 준비 |
| `permitting_development` | 80 | 개별 부지 개발·인허가 진행 |
| `site_construction_grid_unverified` | 55 | 고객 시설 공사; 계통 공사는 미확인 |
| `grid_construction` | 40 | 해당 사업과 연결된 전력 인프라 공사 |
| `grid_support_complete` | 35 | 관련 망보강 완료; 수용가 통전·운영은 미확인 |
| `energization_preparation` | 15 | 근거가 있는 시험·통전 준비 |

고객 공장의 건물 공사와 계통 보강 공사는 다르다. 생산설비 시운전, 유틸리티 측 작업 완료, 특정 단계의 부분 통전을 전체 부지의 최종 운영 승인으로 바꾸지 않는다. 공급계약도 서명, 규제 승인, 비용보증, 설비 공사와 실제 통전을 나눠 해석한다. 예컨대 승인 조건이 남은 ESA는 계약의 진척 근거지만 무조건 최종 계약 완료나 통전 완료로 평가하지 않는다.

PG&E의 8개 통전 공정과 앱의 5개 요건은 서로 다른 분류다. Step 3 종료를 앱의 모든 요건 완료로 바꾸지 않는다. 문서 기준일 뒤에 적힌 공정 날짜도 당시 완료로 사용하지 않는다. 이전 통전 분류와 후속 진행 중 분류가 충돌하면 그 불확실성을 기록한다.

## 날짜와 이력

| 필드·기록 | 의미 |
| --- | --- |
| `sourceEvidence.sourceAsOf` | 출처가 설명하는 자료의 기준일 |
| `sourceEvidence.publishedAt` | 해당 출처의 발행일 |
| `sourceEvidence.retrievedAt` | 원문을 실제 취득한 시각 |
| `asOf` | 판단한 진행상태의 기준일; 미확인은 null |
| `evaluatedAt` | 정성 판단을 실제 작성한 시각 |
| 앱 관측의 `capturedAt` | 그 시점의 앱 원장·평가를 저장한 시각 |

확보된 과거 원문을 오늘 다시 검토하면 원래 취득시각과 상태 기준일을 유지하고 평가시각만 새로 기록한다. 보관본이 실제 어느 날짜의 파일인지 확인하며 요청한 URL 날짜나 현재 다운로드 날짜로 바꾸지 않는다. 과거 상태에 오늘 모형을 적용한 점수는 재평가이며 당시 발표됐거나 당시 시스템이 알고 있던 점수가 아니다. 화면 날짜는 KST, 정확한 취득·평가시각은 UTC로 보존한다.

판단은 추가 방식으로 저장한다. 이미 저장한 판단·감사 ID의 내용을 바꾸면 빌더가 거부한다. 새 사실이나 오류 수정에는 새 ID와 새 평가시각을 사용하고 기존 판단을 남긴다. 최신 판단이 미산출 또는 평균 제외로 바뀌었을 때 과거의 점수 있는 판단을 찾아 다시 적용하지 않는다. `knownAt`은 그 시각까지 기록된 판단으로 조회 범위를 제한한다.

## 데이터 생성과 상태 보정

관련 파일은 다음과 같다.

| 파일 | 역할 |
| --- | --- |
| `data/project-stage-inference-fragments/*.json` | 출처·가정·감사 사유를 갖춘 검토 입력 |
| `data/project-stage-inferences.json` | 입력 해시와 이전 판단을 보존한 통합 결과 |
| `data/project-stage-audit-index.json` | 감사 대상의 정확한 원장 ID·이름·권역·유형만 담은 화면용 색인 |
| `data/project-status-reviews.json` | 원장 상태·적격 여부 변경의 별도 검토 이력 |
| `data/reviewed-load-projects.json` | 개별 수용가 원문의 출처·사업 식별을 검토한 기본 입력 |
| `data/bootstrap.json` | 상태 보정을 적용한 초기 원장과 집계·적재 근거 |
| `data/load-project-census.json` | 원문, 동일 사업 연결, 중복·수집 공백을 보존한 조사 원장 |

먼저 출처와 개별 사업 식별을 검토해 기본 원장을 준비한다. 활성 승격이나 운영·철회 제외는 별도의 상태 검토로 적용하고 최종 `bootstrap`을 만든다. 그 결과로 조사 원장과 Pages 자료를 재생성한다. 정성 판단 입력의 `projectSnapshot`은 이렇게 확정된 정확한 원장 행에 연결한 뒤 통합한다. 판단을 조회할 때도 현재 행과 전체 스냅샷이 일치해야 적용하므로 같은 ID의 내용을 바꾼 뒤 오래된 판단을 그대로 붙이지 않는다.

상태 보정은 기존 행의 `status`, `state`, `eligible`, `exclusionReason`만 바꿀 수 있다. 원문 이름·ID·상태 문자열·날짜·MW는 보존한다. 새 고객을 만들려면 먼저 출처·사업 식별 검토를 통과해야 하며 상태 보정만으로 기록을 생성하지 않는다. 이전 상태와 다음 상태는 정확히 이어져야 한다. `data:reviewed`의 기본 운영 입력은 검토 수용가 자료를 병합한 뒤 상태 보정도 적용한다.

`apps/grid-atlas`에서 생성 결과를 변경하지 않고 확인한다.

```sh
npm run data:reviewed:check
npm run data:status:check
npm run data:census:check
npm run data:inferences:check
```

검토를 완료한 입력을 재생성할 때에는 `npm run data:status`, `npm run data:census`, `npm run data:inferences`를 사용한다. 정성 추정 명령은 통합 결과와 감사 대상의 화면용 색인을 함께 생성·검사한다. 추정 빌더는 기본적으로 기존 통합 결과를 읽어 이전 판단을 보존한다. 입력을 고쳐 검사만 통과시키는 대신 새 판단을 추가해야 한다. `--check`는 데이터셋의 일관성·해시·날짜·감사 연결과 재생성 결과를 확인하며 원문을 새로 수집하거나 판단 내용의 사실성을 자동 인증하지 않는다.

CI는 상태 보정과 정성 판단의 생성 결과를 검사한다. 검사 통과, GitHub Pages 배포, 새 원문 수집, DB 적재·관측 저장은 각각 다른 작업이다. 정성 판단을 체크인하거나 Pages를 게시해도 자동 뉴스 평가, 주간·월간 프로젝트 갱신 또는 운영 DB의 평가 저장이 활성화되지는 않는다.

## 2026-10-12 검토 결과

이번 반영은 공식 신청·기술검토·계약·공사 자료와 고객 공시·언론보도를 대조한 일회 검토 결과다. 원문 해시와 실제 취득시각은 각 판단의 `sourceEvidence`에 보존한다.

- 개별 판단 1,343건 중 단계 추정 1,204건. 이 중 수용가 단계 판단은 814건이며, 운영·철회 판단에는 활성 병목점수를 부여하지 않았다.
- 현재 평균에 적용되는 정성 판단은 825건(수용가 435, 발전·저장 390). 기존 공식 단계 모형도 함께 사용한다.
- 현재 수용가 활성 원장 632건 중 평가 610건, 미산출 22건, 평균 68.4508196721점. 전체 활성 원장 8,991건 중 평가 7,655건, 평균 66.9144350098점.
- MISO 공식 후속 자료에서 철회가 확인된 발전·저장 101건은 현재 활성 집계에서 제외했다. 과거 관측·원문의 진행 상태와 용량은 보존했다.
- 원문 참고 행을 활성 신청으로 단순 전환하지 않고, 단일 고객 요청으로 식별한 333건의 CENSUS 대표를 연결했다. 기존 원문은 유지하고 요청 MW·범위가 불명확하면 용량을 비워 두었다. 조사 원장의 사업·신청 수는 1,288건으로 유지했다.
- 원장에 주가 없던 PJM 요청은 공식 지명 자료 또는 동일 고객의 로컬 접속설비 위치를 대조했다. 전력회사 영업지역만으로 주를 지정하지 않았다.
- 조사 감사 3,093건 중 실제 검토 1,957건과 미검토 1,136건을 구분했다. 감사 항목 수는 전국 프로젝트 확보율이 아니다.

이후 자료 갱신으로 집계는 바뀔 수 있다. 위 수치는 이 날짜의 검증 결과이며 대시보드는 당시 선택 범위의 집계를 표시한다. 과거 원장이 알려주지 않는 날짜에 점수를 보간하거나, 예상하는 병목 추세를 만들지 않았다.
